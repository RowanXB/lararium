# Binance (M7) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Connect a Binance account through its REST API with a key that can only read, so that:
- every wallet is a ledger account whose balance is what Binance reports;
- every record type the read API documents is fetched, stored typed and posted;
- each sync compares the change between two reports with the records in between;
- deposits and withdrawals carry the hash, network and addresses M8 will pair on;
- every asset held has a daily price.

**Architecture:**
- A new package `lararium.modules.finance.binance`:
  - a queries-only client (allowlist, HMAC and Ed25519 signing, weight-aware pacing);
  - a catalogue of endpoints and fields, the single source for fetching, parsing, the typed tables and the tests;
  - a sync (gate → balances → records by cursor → raw records);
  - a versioned normalizer (raw records → accounts, instruments, reported snapshots, ledger rows, typed `finance.binance_*` tables), then the opening adjustment and the reconciliation;
  - prices from Binance's daily bars, with CoinGecko as an optional second source.
- Wallet accounts are `hybrid`: the latest report is the balance, records move it between reports.
- A new FX source, the ECB's reference rates, which only fills gaps.
- Deposits and withdrawals post their contra through `transfer_contra`; the worker's `heal_transfers` pairs them.

**Tech Stack:** as plans 3 to 5 (FastAPI, SQLAlchemy async, PostgreSQL 18, raw-SQL Alembic, Procrastinate, httpx, React/Vite/TanStack, hey-api). Ed25519 uses `cryptography`, already a dependency. No new runtime dependency.

**Spec:** `docs/superpowers/specs/2026-11-22-binance-design.md` (read it first) and its catalogue `docs/superpowers/specs/2026-11-22-binance-endpoint-fields.md` (called "the catalogue" below; its section and label names are used as they are). Parents: `2026-11-11-financial-gate-phase1-design.md` (§7.4, §8, §9, §11.2, §14), the M4 design (§5.6 to §5.8) and the M5 design (§5.7, §5.11).

**Builds on:** `main` at or after `68e0bec`. It needs nothing from M6 (PR #32). Migrations are numbered from the next free number on `main` when implementation starts (`0030` on 2026-11-23; written `NN`, `NN+1`, … below); renumber if another branch merges first.

**Two phases, each mergeable on its own:**
- **Phase A (Tasks 1–14):** everything the owner's account has exercised (Spot, Earn's flexible product, deposits, withdrawals, trades, convert, dividends), plus the machinery every product shares. After Phase A the owner's Binance is complete in the ledger.
- **Phase B (Tasks 15–23):** every other product, built from the catalogue's documented shapes. Each task adds endpoints to the same machinery.

## Decisions

Choices the design leaves to the builder, made here so tasks don't have to:

1. **Package layout**, all in `lararium.modules.finance.binance`:

   | File | What it holds |
   |---|---|
   | `client.py` | `BinanceClient`, the signers, `Limiter`, the errors |
   | `catalogue.py` | `Endpoint`, `Field`, `ENDPOINTS`, `FIELDS`, `WALLETS` |
   | `parse.py` | response body → validated rows; unknown fields and enum values |
   | `sync.py` | `BinanceConnector`, the gate, `due` |
   | `fetch.py` | windows, cursors, paging, the trade symbol sets |
   | `balances.py` | wallet reports → reported snapshots and position tables |
   | `accounts.py`, `instruments.py` | find or create |
   | `models.py`, `tables.py` | the `finance.binance_*` models and their upserts |
   | `normalize.py` | the run: dispatch, the three shared rules, the report |
   | `records/` | one module per family: `capital.py`, `spot.py`, `earn.py`, `transfers.py`, `margin.py`, `futures.py`, `options.py`, `loans.py`, `fiat.py` |
   | `opening.py`, `reconcile.py` | |
   | `prices.py` | bars → EUR prices; the CoinGecko fallback |

   The ECB source is `lararium.modules.finance.ecb`. Routes go in `connections_api.py`, next to the IBKR ones.

2. **The catalogue is code and document at once.** `catalogue.py` holds, per label, an `Endpoint` and its `Field`s, transcribed from the catalogue document. A test parses the document (its "Index of labels" for method, host and path; the field table under each label's heading for the fields) and fails when the two disagree (Task 2), so neither drifts. When a real response differs, both are corrected in the same commit.

3. **Columns come from the catalogue by rule**, so this plan lists no column:
   - one table per record or report label, `finance.binance_<label with _ for ->` (`binance_deposits`, `binance_earn_flexible_rewards`); `time` has none (it only sets the clock);
   - one column per field, named by the field's path in snake case (`completeTime` → `complete_time`, `commissionRates.maker` → `commission_rates_maker`);
   - an array of objects is a child table `<parent>_<path>` keyed by the parent's key and the element's position; an array of scalars is a `text[]` or `numeric[]` column;
   - `decimal string` and `number` amounts are `numeric` with the non-finite CHECK; `integer` ids are `text` when the catalogue marks them as ids, else `bigint`; epoch-millisecond times are `timestamptz`; text times keep a `text` column as given plus a `timestamptz` one; booleans `boolean`; everything else `text`;
   - every column is nullable unless the catalogue marks the field required;
   - a record table has `transaction_id uuid REFERENCES finance.transactions ON DELETE SET NULL` (null when the row is not posted), `connection_id`, and a UNIQUE on the record's key (Decision 5); a report table is keyed by `(connection_id, snapshot_at, <the row's id fields>)`, `snapshot_at` being the read's `read_from`, and also has `read_to` (Decision 9);
   - tables whose field sets are identical share one table with a `product` column (BFUSD and RWUSD; the ETH and SOL staking histories).

   `test_every_catalogue_field_has_a_column` (Task 4, extended by each later task) walks `FIELDS` and the models and fails on a field with no column. This is the owner's typed-column rule as a test.

4. **Client constants.**
   - Hosts `api.binance.com`, `fapi.binance.com`, `dapi.binance.com`, `eapi.binance.com`, `papi.binance.com`; `https` only; redirects off; `User-Agent: Lararium/<package version>`.
   - `ALLOWED = {(e.method, e.host, e.path) for e in ENDPOINTS.values()}`. A request not in it raises `RequestRefused` before any I/O. `POST` appears only for `funding-asset` and `user-asset`.
   - `recvWindow=10000`; `timestamp` from the local clock plus the offset measured against `/api/v3/time` at the start of each sync.
   - Signing: the query is `urllib.parse.urlencode(..., quote_via=quote, safe="")`; HMAC signature is the hex SHA-256; Ed25519 is the base64 signature, percent-encoded; `signature` is appended last. For a POST the parameters stay in the query and the body is empty.
   - Limits per minute: `/api` 6,000; SAPI per endpoint 12,000 (IP) or 180,000 (UID); `fapi`, `dapi` and `eapi` publish theirs only in their own `exchangeInfo` `rateLimits` (`REQUEST_WEIGHT`), which the task that first calls the host reads at the start of a sync (600 a minute until read). The limiter keeps each under 80%, spaces any two requests by 100 ms, and blocks a bucket for the rest of the minute when a used-weight header reaches 85% of its limit.
   - Errors:
     - HTTP 401, or Binance codes `-2014`, `-2015`, `-1022` → `BinanceKeyRejected` (a `CredentialRejectedError`), message `"Binance rejected the key (code <code>)"`;
     - HTTP 418 → `BinanceBanned`; the sync fails at once;
     - HTTP 429 → wait `Retry-After` (1 to 300 s, default 30) and retry, at most 3 times;
     - `NOT_PRESENT = {-3003, -30105, -6021, -5026, -4047, 403004}` or HTTP 404 → `BinanceNotPresent(code)`, which a history walk treats as "this window, or this product, is not available" (Decision 7);
     - anything else → `BinanceError(http_status, code)`, an ordinary failure.
   - No message ever contains key material, a URL, an address or a hash. The sleep and clock are injectable.

5. **Keys.** `external_id = "<record>:<id>"`, the id being the field or fields the catalogue names as the record's id (joined with `:`; trades are `spot_trade:<symbol>:<id>`). A record with no id: `"<record>:<sha256 of its canonical JSON, first 24 hex>:<occurrence>"`, occurrence counted among rows identical in every field within one response set; the raw record's content is `{"row": <the row>, "occurrence": <n>}` for such records, so two identical rows are two raw records. Derived transactions append a suffix: `:fee`, `:refund`, `:funding`.

6. **Connector state.** `config` holds `key_type`, `uid`, `account_map` (wallet name → account id), `cursors` (label → `{"fetched_to": ms, "backfilled_to": ms, "complete": bool}`; `label:symbol` for trades → the last trade id), `first_sync_done`, `not_present` (labels), `normalized_through` (the last raw record id normalised), `flags` (the names already flagged). The sync's returned cursor is `{"fetched_at": <ms>}`.

7. **Fetching.**
   - `due`: no successful sync yet, or `now − fetched_at ≥ 4 hours`, or the owner asked for this sync (`SyncContext.requested`, Task 3).
   - Each endpoint's `Endpoint` gives `window_days` (the catalogue's maximum span minus one day), `lookback_days` (documented, or `None`), the paging style and page size, and the name of its time parameters.
   - **First walk** of a label (its cursor not `complete`): **backwards, newest window first**, from now towards the earlier of 2017-07-01 UTC and `lookback_days`. `fetched_to` is set to now when the walk starts, and `backfilled_to` to the start of each window as it is stored, so an interrupted walk continues backwards from `backfilled_to`.
     - `BinanceNotPresent` on the newest window: the product is not present; the label goes to `not_present`.
     - `BinanceNotPresent` on an older window: the endpoint's history ends there; the walk is `complete`. Walking backwards is what makes this rule safe: every window newer than the refused one has already been stored.
     - An empty answer never ends a walk (an old window can be empty and an older one not).
   - **Later walks:** forwards, oldest window first, from `fetched_to − 7 days` to now.
   - Each window is stored in its own short transaction through `ctx.session_factory`, with its raw records and the cursor. A label in `not_present` is retried once every 7 days.
   - **Trade symbols.** First sync: every symbol in `exchangeInfo`. Later: symbols whose base and quote are both in the set of assets the connection has ever seen (`binance_assets_seen`, Task 4). Sweep: every symbol with one given asset on either side, from a given time (Task 7).
   - Daily account snapshots (`snapshot`) are fetched on the first sync only.

8. **Wallets.** `WALLETS` maps Binance's `walletName` to a key: `Spot` → `spot`, `Funding` → `funding`, `Earn` → `earn`, `Cross Margin` → `cross_margin`, `Isolated Margin` → `isolated_margin`, `USDⓈ-M Futures` → `um_futures`, `COIN-M Futures` → `cm_futures`, `Options` → `options`, `Trading Bots` → `trading_bots`, `Copy Trading` → `copy_trading`; plus `loans` and `portfolio_margin`, which are not in that list. Accounts are named `Binance <walletName>` (`Binance Crypto Loans`, `Binance Portfolio Margin`). An unknown `walletName` gets the key `other:<name>` and the account `Binance <name>`.

9. **Time.** `occurred_at` is the record's time field in UTC (`occurred_tz="UTC"`); `booking_date` its UTC date.
   - **A report is one balance request, not one sync.** Each balance request has its own bracket on Binance's clock: `read_from` just before it is sent, `read_to` just after its response. A wallet's snapshot has `as_of = read_from` of the request its balance came from; `as_of_date` is its UTC date.
   - **Consistent cutoff.** A balance read while a movement was happening may or may not contain it, and the `hybrid` rule adds every posting after `as_of`, so such a read would count the movement twice or not at all. After the records are fetched, a read is **ambiguous** when any fetched record of the connection has its time inside `[read_from − 2 s, read_to + 2 s]` (the 2 seconds cover times Binance gives to the second). An ambiguous read is repeated, and the history labels walked forwards again, at most 3 rounds. A read still ambiguous after that writes no snapshot in this sync: the wallet keeps its previous snapshot and the records after it, and the next sync reads it again.
   - Two wallets read one after the other need nothing more: a transfer between their two reads is after the first wallet's `as_of` (its posting is added) and before the second's (already in its balance).

10. **Posting conventions.**
    - A swap: the given side is a plain negative posting; the received side carries `cost_per_unit = given / received` in the given instrument. A spot trade uses Binance's `price` (`cost_per_unit` for the buyer's base, `price_per_unit` for the seller's base) and `quoteQty` for the other side.
    - Rounding: the residual a rounded price leaves is one Unassigned posting (memo "rounding") when it is within |quantity| × half a unit of the price's last decimal place plus the instrument's tolerance; beyond that the normaliser fails naming the record's key (M5 §5.7).
    - Fees: a posting with `is_fee`, and one Unassigned posting per asset for their total.
    - Income (dividends, rewards, futures income, rebates): the amount against Unassigned.

11. **Reconciliation** (design §5.11), in `reconcile.py`:
    - an interval is two consecutive `reported` snapshots of one (account, instrument); its reported change is the difference; its posted sum is the sum of non-void postings with `as_of(before) < occurred_at ≤ as_of(after)`;
    - a difference exists when `|reported change − posted sum|` exceeds the instrument's tolerance (the ledger's `tolerance(decimals)`);
    - futures accounts compare with the change of `wallet_balance` in `binance_um_account_assets` / `binance_cm_account_assets` instead of the snapshot;
    - the Earn allowance: `0 < reported change − posted sum ≤` the largest `REALTIME` reward of that asset in the 48 hours before `as_of(after)` is not a difference;
    - intervals checked in a run: the newest of every (account, instrument), and every interval containing the `occurred_at` of a posting the run created, changed or removed;
    - `finance.binance_reconciliation_differences` (`account_id`, `instrument_id`, `from_at`, `to_at`, `reported_change`, `posted_sum`, `opened_at`, `closed_at`), unique on the first four; a difference that no longer holds gets `closed_at`;
    - warning text: `"Binance <wallet>: <symbol> changed by something no record explains between <from> and <to> (UTC)"`, no amount.

12. **Opening adjustment** (design §5.8), in `opening.py`: for every (account, instrument) with a reported snapshot, `earliest reported quantity − sum of non-void postings with occurred_at ≤ its as_of`, excluding the opening itself. Non-zero → `opening:<wallet key>:<instrument id>` against the Opening balances system account, `booking_date` the day before the account's earliest other record (or the snapshot's date when it has none); zero → the opening is voided if it exists. It runs after every normalise once `first_sync_done`.

13. **Prices.**
    - `EUR_QUOTES = ("USDT", "USDC", "FDUSD", "BTC", "ETH", "BNB")`. Path for an asset A on day D, first that has a bar on D: `AEUR` close; else `EURA` close inverted; else for Q in `EUR_QUOTES`: `AQ` close (or `QA` inverted) × Q's own EUR price by the same rule, one level deep.
    - The EUR price is `record_price(instrument, quote=EUR, price, as_of_date=D, source="binance")`, rounded to 12 significant digits.
    - Bars are fetched from each asset's first held day (its earliest posting or snapshot) to yesterday UTC, 1,000 bars a request, and stored in `finance.binance_klines`.
    - CoinGecko: only when `Settings.coingecko_api_key` is set. Base `https://api.coingecko.com/api/v3`, header `x-cg-demo-api-key`, at most 25 calls a minute; ids from `/exchanges/binance/tickers` (paged) for every asset seen; prices from `/coins/{id}/market_chart/range` in `vs_currency` = the reporting currency when `/simple/supported_vs_currencies` lists it, else `usd`; the 00:00 UTC point of D + 1 is the price of D; source `coingecko`; never written for a day with a `binance` price.

14. **ECB.** `https://api.frankfurter.dev/v1/<from>..<to>?base=EUR` (no key; check the path against Frankfurter's current documentation when implementing) gives `{"rates": {"<date>": {"<ccy>": rate}}}`. One row per date and currency that is an existing fiat instrument: `record_fx_rate(base=EUR, quote=<ccy>, rate, as_of_date, source="ecb")`, skipped when `finance.fx_rates` already has a rate between EUR and that currency on that date from another source, in either direction; an `ecb` row is deleted when such a rate arrives later. A daily periodic task at 16:30 UTC fetches from the day after the latest `ecb` date (or from the earliest `booking_date` of any posting) to today.

15. **Notifications** use the wording of the design's §5.14; one message per run, the flags on one line.

## Global Constraints

- **Everything in plans 1 and 3 to 5 still applies:**
  - Python 3.13, the uv lockfile enforced, ruff, pyright strict on `src/`, import-linter;
  - PostgreSQL 18; `NUMERIC`/`Decimal`/strings, and the word `float` nowhere in `src/`; UUIDv7; UTC `timestamptz` plus a separate `date`;
  - English UI copy and docs (only the README also has `README.zh-CN.md`);
  - AGPL-3.0-compatible dependencies only.
- **Git.** Branch `feat/claude-binance` (Phase A) and `feat/claude-binance-products` (Phase B); commit messages `<type>: <summary>`; signed commits (`local-signed-git-commit` skill); commit by explicit path, never `git add -A`.
- **Writes.** Every write goes through `command_context` and is audited. The worker acts as `Actor("connector", "binance")`, the ECB task as `Actor("system", "ecb")`, the API as the owner.
- **Errors.** Domain code checks every rule the database enforces before writing. Request errors are 4xx with a readable `message`, never 500.
- **Queries only.** No code path can send a request outside `ALLOWED`. A reviewer rejects any new `POST` that the catalogue does not list as a query.
- **Synthetic data only.**
  - Fixtures are hand-written, shaped like the catalogue: invented ids, assets (`AAA`, `BBB`, `STB` for a stablecoin; real codes only where a rule depends on them: `EUR`, `USDT`, `BNB`, `LD`-prefixed), addresses (`0x` + 40 hex of a repeated digit), hashes and amounts.
  - The owner's probe output stays in `private/m7-probe/`. Only its `summary*.txt` files may be read; nothing under `raw/`. No value, count, date or asset from it reaches code, tests, commits or PR text.
- **Network.** No outbound HTTP in tests: `httpx.MockTransport`, an injected sleep and clock.
- **Secrets and personal data.** Key material is a `Secret` everywhere and never appears in logs, audit args, events, API responses, warnings or notifications. Addresses and hashes never appear in logs, warnings or notifications; the identifier registry audits a `chain_address` as it does a bank account number.
- **Tests.** They run on the remote Docker host: `DOCKER_HOST=ssh://docker-test make check`. `make check` must be green before each commit that ends a task.

## Review Focus

Inputs the design implies that the main-path tests would not hit, most likely first. Each has a test in its owning task:

- **The same record in two overlapping windows, with its status changed in between** (a withdrawal that was processing and then failed): one typed row, the withdrawal no longer a transfer, one refund, and re-running writes nothing (Task 6: `test_failed_withdrawal_is_refunded_not_voided`).
- **A movement while the balances are being read** (a deposit credited between the Spot request and its response): the wallet is read again, its snapshot is cut after the deposit, the balance is right and no difference appears (Task 5: `test_movement_during_balance_read_is_not_counted_twice`).
- **A record that arrives after the report that already contains it:** the balance does not count it twice, and the interval it belongs to closes its difference (Task 7: `test_late_record_closes_its_interval`).
- **An asset bought and sold between two syncs that the account never showed:** the quote asset's unexplained change triggers one sweep, which finds both trades, and no difference is left (Task 7: `test_round_trip_through_unseen_asset_found_by_sweep`).
- **An `LD`-prefixed asset in `/api/v3/account` next to the same asset in Earn:** counted once, in Earn (Task 5: `test_ld_assets_never_counted`).
- **An IBKR account valued through IBKR's EUR rate on a day the ECB also publishes one:** its value does not change when the ECB rates are loaded (Task 9: `test_ecb_never_changes_an_ibkr_valuation`).

### Task 1: The client

**Files:**
- Create: `binance/__init__.py`, `binance/client.py`, `tests/finance/binance/test_client.py`

**Interfaces:**
- Produces:
  - `class Signer(Protocol)`: `kind: Literal["hmac", "ed25519"]`, `def sign(self, payload: str) -> str`;
  - `class HmacSigner(secret: Secret)`, `class Ed25519Signer(private_key_pem: Secret, passphrase: Secret | None)`; both have a `__repr__` that shows nothing;
  - `class Limiter(clock, sleep)`: `async def acquire(self, bucket: str, weight: int, cap: int) -> None`, `def block(self, bucket: str, seconds: float) -> None`;
  - `class BinanceClient(http: httpx.AsyncClient, api_key: Secret, signer: Signer, *, clock=time.time, sleep=asyncio.sleep, limiter: Limiter | None = None)`:
    - `async def sync_clock(self) -> None`;
    - `def now_ms(self) -> int` (Binance's clock);
    - `async def call(self, endpoint: Endpoint, params: Mapping[str, str | int | bool] = {}) -> JSONValue`, which parses numbers as `Decimal`;
  - `RequestRefused`, `BinanceError`, `BinanceKeyRejected`, `BinanceBanned`, `BinanceNotPresent` (Decision 4);
  - until Task 2 lands, `Endpoint` is a small frozen dataclass in `client.py`'s tests; Task 2 moves it to `catalogue.py`.

**How `sync` runs:**
1. If not `due(cursor, now, ctx.requested)`, return the cursor unchanged (no request).
2. `open_client`, `sync_clock`, then `api-restrictions` → `gate_problem`; a problem raises `CredentialRejectedError("this key can do more than read: <field>")`.
3. `spot-account` for `uid`; a `uid` differing from `config["uid"]` fails the sync.
4. The balance labels (`kind` `account`, `balance`, `position`) of the phases built so far, each read with its bracket and stored as raw records with `request = {"read_from_ms": …, "read_to_ms": …}`.
5. Every history label's `walk`; then the trade walks (Decision 7).
6. `settle_reads` (Task 5): repeat ambiguous balance reads and step 5's forward walks, at most 3 rounds (Decision 9).
7. `normalize(ctx)` (Task 6), `opening` and `reconcile` (Task 7), prices (Task 10).
8. Return `{"fetched_at": now_ms}`.
