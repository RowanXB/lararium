# IBKR Flex (M5) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Connect the owner's Interactive Brokers accounts (a GIA, the ISA's companion general account, and a closed ISA) through the Flex Web Service and a one-off upload, so that:
- positions, per-currency cash, trades, conversions and cash movements sync daily into the ledger;
- IBKR's reports check them;
- IBKR's prices and FX rates value them on every day of the history;
- Monzo ↔ IBKR and ISA ↔ GIA transfers pair through M4's engine.

**Architecture:**
- A new package `lararium.modules.finance.ibkr` with four parts:
  - a Flex client (HTTP, pacing, error codes);
  - a parser (XML → section rows as strings);
  - a sync (fetch windows → documents and raw records);
  - a versioned normalizer (raw records → ledger rows, typed `finance.ibkr_*` tables, prices, FX rates, reported snapshots, reconciliation).
- IBKR's records are the ledger's truth; the accounts are in `transactions` mode, as Monzo's are.
- Deposits and withdrawals post their contra through `transfer_contra`, and the worker's existing `heal_transfers` pairs them.

**Tech Stack:** as plans 3 and 4 (FastAPI, SQLAlchemy async, PostgreSQL 18, raw-SQL Alembic, Procrastinate, httpx, React/Vite/TanStack, hey-api). The parser uses the standard library's `xml.etree.ElementTree`. No new runtime dependency.

**Spec:** `docs/superpowers/specs/2026-11-18-ibkr-flex-design.md` (the M5 design; read it first), with its parent `docs/superpowers/specs/2026-11-11-financial-gate-phase1-design.md` (§7.1, §7.3, §9, §14) and the M4 design `docs/superpowers/specs/2026-11-15-transfer-matching-design.md` (§5.6, §5.7).

**Builds on:** `main` with PR #12 (M2 import) merged. M5 needs its `core.documents` and `LocalDocumentStore`. Migrations start at `0019`; renumber if another branch merges first. Do not start before #12 is on `main` (the owner holds dependent PRs until their base merges).

## Decisions

Choices the design leaves to the builder, made here so tasks don't have to:

1. **Package layout.** All in `lararium.modules.finance.ibkr`:

   | File | What it holds |
   |---|---|
   | `client.py` | `FlexClient`, errors |
   | `parser.py` | `parse_statement` and the field lists |
   | `fields.py` | the required and known fields per section, the single source for the parser, the normalizer and the README table |
   | `sync.py` | `IbkrConnector` |
   | `normalize.py` | rows → ledger |
   | `instruments.py` | find or create a listing |
   | `reconcile.py` | |
   | `tables.py` | upserts into the `finance.ibkr_*` tables |

   The routes go in `connections_api.py` and `api.py`, next to the Monzo ones.
2. **The IBKR facts this plan relies on** (IBKR documentation, checked 2026-11-18): the design's §3.1. Sources:
   - <https://www.interactivebrokers.com/docs/web-api/api-reference/send-request.md>
   - <https://www.interactivebrokers.com/docs/web-api/flex-web-service/error-codes.md>
   - <https://www.ibkrguides.com/clientportal/performanceandstatements/flex3.htm>
   - <https://www.ibkrguides.com/reportingreference/reportguide/activity%20flex%20query%20reference.htm> and its section pages
   - <https://www.ibkrguides.com/clientportal/performanceandstatements/flex.htm>
   - <https://www.interactivebrokers.com/en/pricing/commissions-spot-currencies.php>
3. **Client constants.**
   - `BASE = "https://ndcdyn.interactivebrokers.com/AccountManagement/FlexWebService"` and `VERSION = "3"`.
   - Header `User-Agent: Lararium/<package version>`.
   - `MIN_SPACING = 6 s` between any two requests of one client; `FIRST_POLL = 5 s`; `POLL_BUDGET = 120 s`.
   - The sleep function is injectable, so tests don't sleep.
   - Error mapping:
     - 1011–1016 → `FlexConfigError(code, message)`, a subclass of `CredentialRejectedError`;
     - 1001, 1003–1009, 1018, 1019, 1021 → `FlexRetryableError(code)`; inside the poll loop 1009 and 1019 wait and poll again;
     - anything else → `FlexError(code)`.
   - Messages never contain the token or a URL.
4. **When a sync is due.** `due(cursor, now) -> bool` is true when `cursor["fetched_at"]` is missing or earlier than the latest 06:00 Europe/London at or before `now`. A sync that isn't due returns the cursor unchanged without any request (the M3 worker still records success, so a not-due tick is harmless).
5. **Windows.**
   - `yesterday` is `now`'s London date minus 1.
   - First sync: `[yesterday − 364, yesterday]`, then earlier 365-day windows back to `max(min dateOpened, date(year − 4, 1, 1))` when an account opened before the first window.
   - Later syncs: `[fetched_to − 6, yesterday]`, split into 365-day pieces if longer.
   - Fetched oldest first.
   - The cursor is `{"history_from": "YYYY-MM-DD", "fetched_to": "YYYY-MM-DD", "fetched_at": ISO instant}`.
6. **The closed ISA is uploaded.** Flex Web Service cannot select a closed account, and a Client Portal run that includes it works (verified 2026-11-18).
   - Route: `POST /connections/{id}/ibkr-statement` (`upload_ibkr_statement`).
   - The upload goes through `ingest_statement` (Task 3), the same function a fetched statement goes through.
   - The limit is **64 MiB**: a one-year, all-sections, three-account file was about 10 MB, so M2's 5 MiB is too small.
7. **Raw records.**
   - `record_type` is `ibkr.<section>`.
   - `content = {"account": accountId, "period": {"from": fromDate, "to": toDate}, "attributes": {...}}`, with the attributes as IBKR sent them, strings only.
   - `request = {"query_id", "fd", "td", "document_sha256"}`; for an upload, `{"upload": filename, "document_sha256"}`.
8. **Normalizer version** `NORMALIZER_VERSION = "ibkr-norm-1"`, stored in the connection config. Bumping it replays every raw record on the next sync, which is how later field additions backfill (Monzo's pattern).
9. **Keys and rows.**
   - External ids: `trade:<transactionID>`, `cash:<transactionID>`, `ca:<transactionID>`, `transfer:<transactionID>`, `opening:<accountId>:<instrument_id>`.
   - Two rows with one key and different attributes, in one ingest, raise `FlexDataError` naming the section and key, never values.
   - Every ledger write goes through `upsert_connector_transaction`; the `ibkr_*` row is upserted with it, and written only when it differs.
10. **Booking and time** (design §5.8):
    - `occurred_at` from `dateTime` with its zone suffix: `EST`/`EDT` → `America/New_York` (the only ones the audit saw), `GMT`/`BST` → `Europe/London`; any other suffix raises `FlexDataError`.
    - A date-only value is 00:00 `America/New_York`.
    - `booking_date = reportDate`, and `value_date = settleDate` or `settleDateTarget`.
11. **Snapshots and prices.**
    - Reported snapshots: `as_of` is 23:59:59.999999 `America/New_York` on the report date, kind `reported`.
    - Prices go through `record_price(source="ibkr")`, FX rates through `record_fx_rate(source="ibkr")`.
    - A price of 0, or a missing one, is not recorded.
12. **Connection lifecycle.**
    - `POST /connections/ibkr` creates the connection with status `healthy`, stores the token as purpose `flex_token`, sets `credential_expires_at` to the start of the day after the expiry date in Europe/London, and defers `sync_connection`.
    - `IbkrConnector.check_access` returns `True` (there is no approval step).
    - `PUT /connections/{id}/ibkr` replaces token, expiry and query id, moves `needs_reauth` → `healthy`, clears `last_error` and `expiry_notified_for`, and defers a sync.
13. **Reconciliation warnings** are `IBKR ···1234 <SYMBOL> differs from IBKR's report on YYYY-MM-DD by <amount>`, using the last four digits only.
    - They replace the connection's earlier reconciliation warnings, which begin `IBKR ···`.
    - A notification is sent only for a warning text not already present (Monzo's "once per new value").
    - Flagged fields, sections and categories follow the same pattern, prefixed `IBKR flagged: `.

11a. **What the owner's statement looks like** (Task 0's audit, 2026-11-18, of a 365-day fetch and a 7-day fetch through the web service, plus a 365-day Client Portal run including the closed ISA; no values recorded):
    - **Statements and sections.**
      - One `FlexStatement` per account per day (Breakout by Day).
      - Single-row sections (`AccountInformation`, `ChangeInNAV`) are attributes on the section element.
      - Every section is present, mostly empty.
    - **Rows.**
      - Cash Transactions repeat each row at `levelOfDetail="SUMMARY"`, without `transactionID` and with a date-only `dateTime`; read `DETAIL` only.
      - Cash Report has `levelOfDetail="Currency"` rows plus a `BaseCurrency` row (`currency="BASE_SUMMARY"`); read `Currency` only.
      - Conversion Rates repeat for every account and day (about 40 currencies to GBP); de-duplicate by `(reportDate, fromCurrency, toCurrency)`.
    - **Movements.**
      - Internal movements appear only in Transfers (`type="INTERNAL"`, `levelOfDetail="TRANSFER"`, `assetCategory="CASH"`), naming the other side in `account`, all of them the owner's own accounts.
      - Cash Transactions types seen: `Deposits/Withdrawals` (description "CASH RECEIPTS / ELECTRONIC FUND TRANSFERS") and `Other Fees` (the ISA's monthly "ISA MINIMUM ACTIVITY FEE").
    - **Account Information.** `customerType` is `Individual` or `IRA-Individual Savings Account/UK`; the base currency is GBP; `ibEntity` is IB-UK; the tax-lot method is FIFO.
    - **Ids, dates and times.**
      - `transactionID` and `reportDate` are present on every `DETAIL` cash transaction and every transfer.
      - Zones are `EST` and `EDT` only.
    - **Not seen.** No trades, positions, prior-period prices or corporate actions in any account. Those parts are built against IBKR's documentation and synthetic data, and the first real rows are checked by the flags (Decision 13) and reconciliation.

**Not in this plan:**
- the Trade Confirmation query;
- options, futures, bonds, CFDs;
- accrual modelling;
- transfers whose two sides differ in currency or amount (M6);
- adopting a manual account into a connection;
- a tax-wrapper route (the connector sets it from `customerType`);
- reference-based receiving accounts (M6);
- a runtime NAV check (M9);
- eToro and Trading 212 (M6).

## The Flex query and where each field goes

**The owner's query.** The owner's query `lararium` ticks every section, field and option (Task 0). `fields.py` types the sections below; every other section is either **derivable** (Statement of Funds, MTM Performance Summary, Change in NAV, Change in Position Value, Realized and Unrealized Performance, MTD/YTD Performance) and silently skipped, or **flagged when it first has rows**.

**Required fields.** "Req" fields missing from a row raise `FlexDataError`. An attribute not listed here with a non-empty value is flagged.

**Fields in every section.** **accountId** (req) → account. **currency** (req) → instrument. **acctAlias** and **model** → `ibkr_accounts` (both are empty in the owner's data).

**Instrument fields** → the instrument, its identifiers and `ibkr_instruments` (Task 4): `assetCategory`, `symbol`, `description`, `conid`, `securityID`, `securityIDType`, `cusip`, `isin`, `figi`, `listingExchange`, `subCategory`, `multiplier`, `issuer`, `issuerCountryCode`, `underlyingConid`, `underlyingSymbol`, `underlyingSecurityID`, `underlyingListingExchange`, `strike`, `expiry`, `putCall`, `principalAdjustFactor`, `commodityType`, `deliveryType`, `fineness`, `weight`, `serialNumber`.

**fxRateToBase** → each detail table.

## Global Constraints

- **Everything in plans 1, 3 and 4 still applies:**
  - Python 3.13, the uv lockfile enforced, ruff, pyright strict on `src/`, import-linter;
  - PostgreSQL 18;
  - `NUMERIC`/`Decimal`/strings, and the word `float` nowhere in `src/`;
  - UUIDv7;
  - UTC `timestamptz` plus a separate `date`;
  - English UI copy and docs (only the README also has `README.zh-CN.md`);
  - AGPL-3.0-compatible dependencies only.
- **Git.** Branch `feat/claude-ibkr-flex`; commit messages `<type>: <summary>`; signed commits (`local-signed-git-commit` skill); commit by explicit path, never `git add -A`.
- **Writes.** Every write goes through `command_context` and is audited. The worker acts as `Actor("connector", "ibkr")`, and the API as the owner.
- **Errors.** Domain code checks every rule the database enforces before writing. Request errors are 4xx with a readable `message`, never 500.
- **Synthetic data only.**
  - Flex XML fixtures are hand-written, with invented account ids (`U0000001`, `U0000002`), conids, ISINs (with valid check digits), symbols and amounts.
  - The owner's real statements go to `private/ibkr-samples/` only.
  - No names, amounts, account ids or dates from them reach code, tests, commits or PR text.
- **Network.** No outbound HTTP in tests: `httpx.MockTransport` and an injected sleep.
- **Secrets and personal data.** The token is a `SecretStr`/`Secret` everywhere. It never appears in logs, audit args, events, API responses, warnings or notifications. Personal fields from Account Information and Transfers are stored (owner's choice), but never logged, put in warnings or notifications, or sent to the API's connection payloads.
- **Tests.** They run on the remote Docker host: `DOCKER_HOST=ssh://docker-test make check`. `make check` must be green before each commit that ends a task.

## Review Focus

Inputs the design implies that the main-path tests would not hit, most likely first. Each has a test in its owning task:

- **The same row in two overlapping windows**, the daily 7-day overlap: written once; the second normalize reports it unchanged and emits no event (Task 5: `test_overlapping_windows_write_once`).
- **A statement that isn't ready yet** (1019, then success, or 1003 on every poll): the first succeeds within one sync; the second fails the sync as an ordinary failure, not `needs_reauth` (Task 1: `test_poll_until_ready`, `test_not_ready_is_ordinary_failure`).
- **An ETF held in both its GBP and its USD listing:** two instruments, two prices, and valuation equal to NAV (Task 4: `test_same_isin_two_currencies_two_instruments`).
- **An internal ISA → GIA cash movement of the same amount as a Monzo payment inside the window:** never paired with the Monzo payment (Task 6: `test_internal_movement_never_pairs_with_monzo`).
- **A token expiring in 10 days:** one reminder across many 30-minute ticks, and another only after the token is updated (Task 3: `test_expiry_reminded_once`).

### Task 2: Field lists and the statement parser

**Files:**
- Create: `ibkr/fields.py`, `ibkr/parser.py`, `tests/finance/ibkr/fixtures.py`, `tests/finance/ibkr/test_parser.py`

**Interfaces:**
- Produces:
  - **`fields.py`.**
    - A `SECTIONS: Mapping[str, SectionSpec]` keyed by XML row element name (the section element for single-row sections), where `SectionSpec(record_type: str, required: frozenset[str], known: frozenset[str], level: str | None)`. It uses XML attribute names, copied from the table above. `level` is the only `levelOfDetail` read (`DETAIL`, `Currency`), or `None` for all.
    - `INSTRUMENT_FIELDS: frozenset[str]`.
    - `DERIVABLE_SECTIONS: frozenset[str]`, the section element names skipped without a flag.
    - `PERSONAL_FIELDS: frozenset[str]`: stored, but excluded from every log, warning and message.
  - **The parser.**
    - `@dataclass(frozen=True) class Row(section: str, account: str, period_from: date, period_to: date, attributes: Mapping[str, str])`.
    - `@dataclass(frozen=True) class Statement(rows: tuple[Row, ...], flagged: frozenset[str])`. Each flag is `"<Section>.<attribute>"`, or `"<Section>"` for an unknown section with rows.
    - `def parse_statement(body: bytes) -> Statement`.
  - **`FlexDataError(ValueError)`**, which names the section and field only.
  - **`fixtures.build_statement(accounts: Sequence[AccountSpec], *, period: tuple[date, date], rows: Sequence[RowSpec]) -> bytes`.** It writes valid synthetic Flex XML. `AccountSpec(account_id, base="GBP", date_opened, date_closed=None)`; `RowSpec(section, account_id, **attributes)`, where missing required attributes are filled with defaults that the tests override.

**Parser rules:**
- A `DOCTYPE` → `FlexDataError`.
- A missing required attribute → `FlexDataError("Trade.reportDate is missing: select it in the Flex query")`.
- An attribute not known for its section, with a non-empty value → kept in the row's attributes (so the raw record holds it) and flagged. An empty one is ignored: the owner's query ticks every field.
- A section neither in `SECTIONS` nor `DERIVABLE_SECTIONS` that has rows → flagged, its rows skipped.
- Rows of another `levelOfDetail` than the section's `level` are skipped.
- **Breakout by Day:**
  - every `FlexStatement` is read, and its `accountId`, `fromDate` and `toDate` set each of its rows' account and period;
  - identical rows from several daily statements collapse to one;
  - Conversion Rates collapse across accounts by `(reportDate, fromCurrency, toCurrency)`;
  - Account Information keeps the latest statement's attributes per account.

- [ ] **Step 1: Write the failing tests:**

  - `async def normalize(ctx: SyncContext, raw_record_ids: Sequence[UUID]) -> NormalizeReport`.

**Order inside one call:** accounts; instruments; FX rates; prices; Cash Reports and NAV; trades, cash transactions, corporate actions and transfers (each sorted by `reportDate`, then `transactionID`); opening adjustments; reported snapshots. Reconciliation is Task 6.

**Posting rules** (design §5.7; fees and taxes are `is_fee` postings on the account, with one Unassigned counterpart per currency):
- **Trades.**
  - A buy carries `cost_per_unit`; a sell carries `price_per_unit`.
  - A conversion (`CASH`, `BASE.QUOTE`) posts `quantity` of BASE with `price_per_unit` in QUOTE, and `proceeds` in QUOTE.
  - A residual beyond `tolerance` in one currency gets one more Unassigned posting (memo `rounding`).
- **Cash transactions.**
  - `Deposits/Withdrawals` use `transfer_contra(source=…, own_account_id, counterparty_identifier_id=None, other_postings=0)`, with `CounterpartyFields(bank_transfer=True)`; the audit shows internal movements only in Transfers.
  - Every other type goes against Unassigned, with `bank_transfer=False`.
- **Corporate actions:** the quantity and proceeds; Unassigned for the remainder.
- **Transfers.**
  - The counterparty identifier is `get_or_create_identifier(ctx, "ibkr_account", account)` when it is set, else none.
  - The amount is `quantity` for securities and `cashTransfer` for cash (`assetCategory="CASH"`).
  - The contra comes from `transfer_contra`, with no cost on the postings.
  - A cash movement that also has a Transfers row is posted from the Transfers row only.
- **Opening adjustments:** design §5.7, computed only when the window is the account's earliest (`cursor["history_from"]` was unset), and only for non-zero values.
